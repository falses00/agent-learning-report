# 事故响应与复盘模板

生成日期：2026-06-30
更新日期：2026-08-08
目标：让事故能变成永久防线，而不是只修一次。

## 1. 事故等级

| 等级 | 示例 | 响应 |
|---|---|---|
| P0 | secret 泄漏、越权写执行、跨租户泄漏 | 立即停用、通知、复盘 |
| P1 | audit 缺失、评测门禁失效、checkpoint 大面积失败 | 冻结发布、修复 |
| P2 | 模型超时、工具失败率升高、成本超预算 | 降级、限流 |
| P3 | 文档或非阻塞测试缺口 | 排期修复 |

## 2. 事故响应流程

```text
检测
-> 分级
-> 限制影响
-> 保全 trace/audit
-> 修复或回滚
-> 复测
-> 复盘
-> 新增 regression
-> 更新门禁
```

## 4. 永久防线

事故结束必须至少产生一个：

- regression case。
- red team case。
- policy rule。
- alert rule。
- runbook 更新。
- release gate 更新。

没有永久防线，事故不算关闭。

## 5. 可机器检查的 Incident Intake

S7 baseline 对每个阻塞原因生成：

```json
{
  "incident_id": "INC-S7-001",
  "severity": "P1",
  "reason_code": "TRACE_COVERAGE_GAP",
  "evidence_refs": ["trace", "audit_chain", "slo_report"],
  "regression": {
    "case_id": "regression-trace-coverage-gap",
    "owner": "sre-course",
    "required": true
  }
}
```

Incident 只有同时满足以下条件才可关闭：

- 影响已经停止或被隔离。
- 原始 trace、audit chain head、SLO slice 和 release version 已保全。
- 临时止损和永久修复分别登记。
- regression case 在修复前能失败，修复后能通过。
- alert、policy、runbook 或 release gate 至少更新一项。
- owner 和验证者明确，不能只写“团队负责”。

Hash chain 能检测导出内容是否被修改，不等于原始存储已经满足 append-only/WORM、访问控制和法务保留要求。

NIST AI RMF 将上线后监测、申诉/覆盖、停用、事故响应、恢复和变更管理放在同一 Manage 闭环。因此复盘不只回答“代码怎么修”，还要记录用户如何报告问题、哪个角色可以停用 Agent、如何验证恢复，以及受影响者何时获得沟通。
